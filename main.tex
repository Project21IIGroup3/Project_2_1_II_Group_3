\section{Introduction}
\label{sec:intro}

Pralax is a desktop application that brings 2D artwork and 3D scenes to life. The way it works is by taking the content on screen and having it respond to the viewer's eye position, creating a parallax effect - as if looking through a window into the scene. The application is
implemented as a Tauri desktop app (Rust shell, SvelteKit + TypeScript frontend).
It currently offers one mode, parallaxed 2D artworks rendered as depth layers;
if time allows, we will add two further modes:
(\textit{i}) 3D scenes created in Blender, and
(\textit{ii}) user-uploaded images projected into a parallax view.
The eye tracking is performed with a regular webcam, so no dedicated hardware is
required.

This document presents the results of the first project phase: the envisioned
software architecture (Section~\ref{sec:arch}), a comparison of the software
components we tested and the approaches we considered, including the performed
tests and the selection criteria (Section~\ref{sec:tests}), the task planning
for the second and third phases with responsibilities
(Section~\ref{sec:planning}), a Gantt chart of the main tasks
(Section~\ref{sec:gantt}), and a risk analysis (Section~\ref{sec:risks}).

\section{Software Architecture}
\label{sec:arch}

Figure~\ref{fig:arch} shows the target architecture as an annotated block
diagram. Green boxes mark components that already exist as phase-1
prototypes, blue boxes are built in phases~2 and~3, and grey boxes are
hardware.

\noindent\textbf{Data flow.} The webcam frames are used by a Python
sidecar process running MediaPipe Face Mesh. The module estimates the viewer's
face/eye position, applies the calibration and exponential smoothing, and publishes
a normalized eye position $(x,y)$ as JSON events to the front-end. The Rust
Tauri shell manages the sidecar lifecycle and exposes a \emph{localhost-only}
IPC bridge, which keeps the tracking data inside the machine (no network
exposure); the messages are small (two coordinates and a timestamp), so JSON
encoding adds latency, but it is so small that it is negligible. The SvelteKit UI receives the
events and passes the position, together with the user settings
(intensity, depth, smoothing - the parameters already prototyped in the
phase-1 overlay), to the parallax engine. The engine renders either a 3D scene
(glTF assets exported from Blender, rendered with Three.js and a camera offset
proportional to the eye position) or a 2.5D artwork (HTML/CSS depth layers that
move at different rates). Scene components are loaded lazily so that modes can
be added without restarting the app.

\noindent\textbf{Status after phase~1.} The eye-tracking controller API
(Tudor), the Tauri window system with lazy loading and the settings overlay
(Federico), the first Blender scene (Justin, Rotem) and the face-to-parallax
mapping prototype (Sotiris) already exist; we also researched the build
system and CI/CD set-up. The IPC bridge, the mode selection UI, the parallax
engine, the CI pipeline and the asset pipeline are built in phase~2
(Section~\ref{sec:planning}).

\section{Software Component Tests and Comparison}
\label{sec:tests}

\subsection{Evaluation criteria and test methodology}

All candidate components were evaluated against the same five criteria:
\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
\item \textbf{C1 - Responsiveness:} frame rate and end-to-end latency
(camera to screen), because a laggy parallax effect is immediately
perceived as broken.
\item \textbf{C2 - Accuracy and robustness:} correct detection under
realistic conditions (glasses, varying lighting, head movement), which
determines how many users can actually use the app.
\item \textbf{C3 - Integration effort:} how easily the component connects
to our chosen stack (Tauri webview, SvelteKit/TypeScript, Python sidecar),
including data formats and licensing friction.
\item \textbf{C4 - Resource usage:} CPU/GPU load, since tracking and scene
rendering must run concurrently on consumer hardware.
\item \textbf{C5 - Maintainability:} documentation, community activity,
permissive licensing and the team's familiarity with the technology.
\end{itemize}

\noindent\textbf{Test setup.} Measurements were taken on the group's
development laptops with a $640\times480$ webcam at 30\,FPS. Each run captured
60\,s of video; the camera-loop frame rate and the per-frame detection latency
were measured with timestamps. Robustness was assessed qualitatively on the
team members (with and without glasses, different rooms and lighting).

\subsection{Eye tracking}

Two eye-tracking implementations were built and tested in phase~1.

\begin{enumerate}[itemsep=2pt,topsep=2pt]
\item \textbf{MediaPipe Face Mesh (Python).} MediaPipe is Google's
open-source framework for on-device perception. It ships pre-trained machine
learning models (\texttt{.tflite}) and exposes a Python API; its face pipeline
first locates the face with the BlazeFace short-range detector and then fits
a 468-point face mesh that includes the eye landmarks. We built a threaded
camera loop using the \texttt{LIVE\_STREAM} running mode with an asynchronous
result callback, so detection runs concurrently with the GUI.
\item \textbf{OpenCV (C++).} OpenCV is the standard open-source computer
vision library; we built a C++ demo using its pre-trained Haar cascade-based face
detector. The fact that it was written in C++, led us to expect that it would offer a speed advantage over MediaPipe Face Mesh.
\end{enumerate}

\begin{table}[H]
\centering
\caption{Speed comparison of the tested face-tracking components.}
\label{tab:speed}
\begin{tabular}{lcc}
\toprule
\textbf{Metric} & \textbf{MediaPipe (Python)} & \textbf{OpenCV (C++)} \\
\midrule
Camera loop rate          & 29.1\,FPS & 29.8\,FPS \\
Detection rate            & 29.1\,FPS & 29.8\,FPS \\
Average detection latency & 2.3\,ms   & 2.1\,ms  \\
\bottomrule
\end{tabular}
\end{table}

\noindent\textbf{Results.} As Table~\ref{tab:speed} shows, both libraries
performed nearly identically: the 30\,FPS webcam is the bottleneck, and both
detectors saturate it. The OpenCV demo was marginally faster ($+0.7$\,FPS,
$-0.2$\,ms), but the qualitative robustness test revealed a decisive
difference: when the user wore glasses, the OpenCV demo detected the face and
eyes only intermittently - from time to time it found something, while
without glasses the detection was more or less instant. MediaPipe kept
detecting reliably in both cases. Since the speed advantage was negligible, we
saw no benefit in spending time calibrating the C++ library to reach
MediaPipe's robustness.
We therefore \textbf{select MediaPipe Face Mesh (Python)} for the eye-tracking
module. It additionally provides 468 facial landmarks, including eye
landmarks, which allow us to refine the eye-position estimate in later phases,
and it integrates directly with the phase-1 controller API (C3, C5).

\noindent\textbf{Considered but not selected.} Dedicated hardware eye trackers
(e.g.\ Tobii) were rejected because they add cost and hardware dependencies,
contradicting the requirement to work with a regular webcam (C3, C4).
Learned gaze-estimation models (L2CS-Net, GazeML) were rejected as unnecessarily
heavy: for a screen-relative parallax effect, the face/eye position suffices,
and the extra latency of a deep gaze model does not buy accuracy we can use
(C1, C4). Dlib's HOG-based detector was considered but not tested further
after MediaPipe's results: it is slower on CPU and less robust than MediaPipe
(C1, C2).

\subsection{3D scene visualisation}

\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
\item \textbf{Approach A - Blender-authored scenes rendered with Three.js
(WebGL) in the webview.} Scenes are authored in Blender (free, large community,
familiar to the artists in the team) and exported as glTF, then rendered with
Three.js. WebGL runs inside the Tauri webview on all three desktop platforms,
and the perspective camera gives full control over the parallax offset.
\item \textbf{Approach B - Babylon.js.} A full 3D game engine in TypeScript
with a richer feature set (PBR, physics, editor). Its added capabilities are
largely unnecessary for static scenes, and it adds bundle size and learning
cost (C4, C5).
\item \textbf{Approach C - CSS 3D transforms.} Pure CSS perspective is
lightweight, but it cannot import scene formats, has no lighting model and
becomes unwieldy for organic scenes (C1, C3).
\item \textbf{Approach D - 2.5D layered artworks (HTML/CSS).} Artwork is
split into depth layers that move at different rates; no GPU work is needed
at all. We prototyped this style in phase~1 with placeholder SVG scenes
(Mona Lisa, Starry Night) and it matches the intensity/depth/smoothing
settings overlay.
\end{itemize}

\noindent\textbf{Tests performed.} In phase~1 we validated (i) the Tauri +
SvelteKit window system with lazy scene loading and a controls overlay
(Federico), and (ii) the asset pipeline by authoring a first 3D scene in
Blender (Justin, Rotem) - which also exposed the export issues (camera
placement, colours) that we address in phase~2. We additionally
researched webview-based rendering with HTML/CSS instead of a GPU-rendered
library and confirmed both are feasible inside Tauri.

\noindent\textbf{Decision.} We \textbf{select Approach A} (Blender + Three.js)
for the 3D scenes, and \textbf{keep Approach D} for the artwork and
user-uploaded-image modes, since it needs no GPU and reuses the tested
settings overlay. Babylon.js (B) is overkill and CSS 3D (C) is too limited.
This hybrid covers all three modes with minimal risk.

\subsection{Parallax effect}

\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
\item \textbf{Approach A - Perspective-camera offset.} The eye position
translates the 3D camera while the scene stays fixed, producing true parallax
with correct occlusion. Naturally compatible with the Three.js renderer.
\item \textbf{Approach B - Layered displacement (2.5D).} Each depth layer
moves proportionally to the eye position divided by its depth. Very cheap,
works for artwork and photos, and its tuning knobs (intensity, depth,
smoothing) already exist in our overlay.
\item \textbf{Approach C - Head-coupled off-axis projection.} The frustum is
recomputed from the physical screen geometry and the eye's position in front
of it (Johnny-Lee/TrackIR style). The most physically correct option, but it
requires precise head-position tracking and per-setup calibration; kept as a
phase-3 stretch goal if time allows.
\item \textbf{Approach D - Shader-based parallax (parallax occlusion
mapping).} Fakes depth inside a texture; limited to surface detail and
unsuitable for real scenes. Rejected.
\end{itemize}

\noindent\textbf{Tests performed.} We built a face-to-parallax
mapping prototype in phase~1: the face-tracking output moves the parallax
effect relative to a reference point, so that looking at a different screen
area changes the view. It works end to end but still needs performance work
(the mapping currently runs in the same loop as detection). The
intensity/depth/smoothing overlay (Federico) provides the parameter interface
for approach B and was tested interactively in the GUI.

\noindent\textbf{Decision.} We \textbf{select a hybrid of A and B}: camera
offset for the 3D scenes and layered displacement for artworks and uploaded
images, with EMA smoothing to suppress tracking jitter. Both are cheap
(C4), instantly responsive (C1), and built on components already tested in
phase~1.

\subsection{Application shell}

We compared three ways to package the application. \textbf{Electron}
bundles its own Chromium and Node.js runtime, which makes installers large and
raises memory use (C4). A \textbf{native desktop toolkit} (e.g.\ Qt/C++) would
give full control but cannot reuse web rendering libraries such as Three.js and
increases the implementation effort (C3). \textbf{Tauri} uses the operating
system's webview with a small Rust core, supports bundling the Python tracker
as a sidecar process, and was validated in phase~1 with the window system,
lazy loading and settings overlay. We therefore \textbf{select Tauri with a
SvelteKit + TypeScript frontend} (C3, C4, C5).
